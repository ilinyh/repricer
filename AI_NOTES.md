# AI_NOTES — журнал ошибок ИИ при разработке

Требование ТЗ: не меньше двух реальных ошибок ИИ. Ниже — ошибки, которые действительно были
допущены в этой работе, как они проявились и что изменилось в коде.

## 1. Пустые метаданные OData принял за «база не поддерживает OData»

**Что сделал.** Первый запрос `$metadata` к демо-базе УТ 11.5 вернул 0 наборов сущностей.
Я решил, что в файловой базе OData не настроен, и начал искать обходные пути (MCP, выгрузку).

**В чём ошибка.** OData был включён, но пуст **состав стандартного интерфейса** — типичное
состояние для УТ 11.5. Проблема решается одним вызовом платформы, а не сменой подхода.

**Как нашёл.** Посмотрел `default.vrd` (там `standardOdata` включён) и проверил состав через
`execute_code`: интерфейс OData был пуст.

**Исправление.** Вызвал `УстановитьСоставСтандартногоИнтерфейсаOData(Состав)` с нужными
объектами (номенклатура, склады, виды цен, характеристики, ключи аналитики, регистры
`ТоварыНаСкладах`, `ВыручкаИСебестоимостьПродаж`, `ЦеныНоменклатуры`). `$metadata` стала
отдавать 24 набора, адаптер заработал. Это же записано в PLAN.md §5 на случай пересоздания базы.

**Вывод.** Прежде чем объявлять функцию «недоступной», проверить настройку её публикации.

## 2. Считал, что httpx сам закодирует пробелы в `$filter`

**Что сделал.** Передал параметры OData через `client.get(url, params={...})` и получил
`400 Bad request` на `$filter=IsFolder+eq+false`.

**В чём ошибка.** `httpx` кодирует пробел как `+` (form-encoding), а OData-сервис 1С понимает
только `%20`; вдобавок кавычки в литералах `datetime'...'` нельзя превращать в `%27` так, как
это делает стандартный энкодер.

**Как нашёл.** Сравнил рабочий URL (собранный вручную) и сгенерированный httpx — отличие было
ровно в `+` и в кодировании кавычек.

**Исправление.** Кодирую query вручную: ключ — с `safe="$"`, значение — с
`safe="'(),$"`, пробел → `%20` (`urllib.parse.quote`). Появился тест живого адаптера, который
ловит такую регрессию.

**Вывод.** У «почти стандартных» API свои правила кодирования; проверять сырой URL, а не только
код ответа.

## 3. Взял поле `Наименование` вместо `Description`

**Что сделал.** В `$select` для `Catalog_Номенклатура` указал `Наименование` — по аналогии с
именем реквизита в конфигурации.

**В чём ошибка.** В OData-представлении 1С поле называется `Description` (стандартное имя
свойства сущности), а `Наименование` — это реквизит объекта, не свойство OData. Сервер ответил
`400: Сегмент пути Наименование не найден`.

**Как нашёл.** По тексту ошибки и по `$metadata`: у `Catalog_Номенклатура` есть `Description`,
`Артикул`, `Ref_Key`, но нет `Наименование`.

**Исправление.** Читаю `Description`, в коде оставил запасной вариант `Наименование` — на случай
другой конфигурации. Покрыто живым smoke-тестом.

**Вывод.** Имена полей OData не равны именам реквизитов метаданных; сверяться с `$metadata`.

## 4. Зарегистрировал форматтеры Jinja как фильтры, а вызвал как функции

**Что сделал.** В шаблонах писал `{{ rub(...) }}`, `{{ num(...) }}`, а в приложении добавил их
через `templates.env.filters`.

**В чём ошибка.** Фильтры в Jinja вызываются через `|`, а прямой вызов ищет имя в глобальных
функциях. Результат — `jinja2.exceptions.UndefinedError: 'num' is undefined` на странице списка.

**Как нашёл.** Упавший тест веб-интерфейса с полным traceback.

**Исправление.** Перенёс `rub/pct/days/num` в `templates.env.globals`, оставив фильтры
доступными. Тест `test_index_shows_zones_and_states` теперь ловит такую ошибку сразу.

**Вывод.** Jinja различает фильтры и глобальные функции; тест на рендер обязателен.

## 5. Забыл `python-multipart` для форм

**Что сделал.** Добавил `Form(...)` и `await request.form()` в веб-слое, зависимости не обновил.

**В чём ошибка.** FastAPI требует `python-multipart` для разбора форм; без него приложение
падает с `RuntimeError: Form data requires "python-multipart" to be installed`, причём только
при первом POST, а не при старте.

**Как нашёл.** Тест сквозного цикла через формы упал на первом POST.

**Исправление.** Добавил зависимость в `pyproject.toml` и `Dockerfile`, установил в venv.

**Вывод.** Тестировать не только GET, но и отправку форм — иначе зависимость всплывёт у
пользователя.

## 6. Массовое подтверждение брало только первый чекбокс

**Что сделал.** В обработчике очереди читал `form.get("ids")` и разбирал строку.

**В чём ошибка.** `FormData.get` возвращает **первое** значение; при нескольких отмеченных
товарах подтверждался только один, остальные молча оставались в очереди. Тесты этого не
замечали, потому что использовали один id или вариант «все».

**Как нашёл.** При подготовке скриншотов сквозного сценария: отметил два товара, а в очередь
вернулся один.

**Исправление.** `form.getlist("ids")`; вариант «все» — отдельная ветка. Добавлен
`test_approve_all_selected_ids` на два выбранных товара.

**Вывод.** Формы с чекбоксами проверять на нескольких значениях, а не на одном.

## 7. Тест ждал смену статуса, не вызывая polling

**Что сделал.** В тесте сквозного сценария крутил цикл `repo.get_decision(...)` в ожидании
статуса `applied`.

**В чём ошибка.** Статус обновляет `service.poll()`; без его вызова решение навсегда остаётся
в `sent`, и тест падал по таймауту (а ошибка выглядела как «статус не меняется»).

**Как нашёл.** Таймаут в `test_approve_send_and_apply` с сообщением «решение не перешло в
applied».

**Исправление.** Ожидание вызывает `service.poll()` на каждой итерации и только потом читает
решение.

**Вывод.** В тестах асинхронного конвейера «ждать» должно означать «ждать, выполняя шаг
конвейера», а не «читать состояние».

## 8. Повторный прогон в режиме «авто» плодил дубликаты

**Что сделал.** Проверку идемпотентности написал только по ожидающим решениям: искал
`pending` (`repo.pending_for`).

**В чём ошибка.** В режиме «авто» решение сразу получает статус `auto`, и проверка его не
видела: каждый прогон создавал новое авто-решение с той же ценой. На демо это дало
«Отправлено: 4» при трёх товарах — два одинаковых авто-решения по одному товару ушли в одной
пачке.

**Как нашёл.** Сквозной прогон через интерфейс: подтвердил 2 решения и увидел в сообщении
«Отправлено: 4».

**Исправление.** Добавил `active_for`/`supersede_active`: активные — `pending`, `approved`,
`auto`, `sent`; при совпадении цели новый не создаётся; при расхождении заменяются все, кроме
`sent` (цена в полёте — новую не создаём до ответа площадки). Регрессионные тесты
`test_auto_rerun_does_not_duplicate` и `test_approved_is_not_duplicated_before_send`.

**Вывод.** Идемпотентность проверять для всех режимов, а не для того, который первым попал
в тест.

## 9. Главная страница падала с 500 при недоступной площадке

**Что сделал.** Обработку ошибок написал только в `POST /run` («Ошибка прогона: …») и считал,
что после неудачного прогона редирект покажет сообщение.

**В чём ошибка.** Редирект ведёт на `/`, а главная страница сама читает товары у площадки и CSV.
При остановленном эмуляторе или битом CSV она падала с 500, и сообщение об ошибке терялось.
Тесты покрывали только успешный путь.

**Как нашёл.** При подготовке `TESTING.md` прошёл сценарий «остановить эмулятор и нажать
„Пересчитать сейчас“» — вместо сообщения получил Internal Server Error.

**Исправление.** `index()` и карточка товара перехватывают ошибку чтения и показывают
«Ошибка чтения данных: …»; добавлен тест `test_marketplace_error_is_shown_not_500`.

**Вывод.** Ошибочные пути проверять так же, как успешные: сообщение об ошибке бессмысленно,
если страница, на которую оно ведёт, сама падает.
